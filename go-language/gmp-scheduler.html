理解 GMP 不会自动修复慢 SQL、缩短远端响应或消除算法开销。它帮你划清：问题发生在执行、排队、阻塞，还是 CPU 资源限制。这些是排查方向，最终结论仍要靠测量。

01先搭一个准确的直觉

官方运行时说明把调度器的工作概括为匹配三种资源：G 是要执行的代码，M 是执行它的 OS 线程，P 是执行普通 Go 代码所需的权利与资源。可以把它们想成车间里的工单、工人和工作台。

G · 工单

有处理进度，可以排队、暂停、恢复。

准确含义：goroutine 的运行时对象，记录栈、保存的执行上下文、状态等。

M · 工人

真正动手执行工单的人。

准确含义：OS 线程。由操作系统调度到逻辑 CPU 上执行。

P · 工作台

工人拿到工作台，才能处理普通工单。

准确含义：运行时执行资源，包含本地运行队列、内存分配缓存等。

为什么还要有 P？只有 G 和 M 不行吗？

可以先把 G 放进一个全局队列，让所有 M 取任务，但竞争同一个队列会带来协调开销。P 提供了分散的本地运行队列与本地资源；M 持有一个 P 工作，暂时不能执行普通 Go 代码时，P 又可以被别的 M 使用。这把“线程身份”和“可复用执行资源”分开了。

本地队列减少集中竞争，工作窃取缓解队列不均衡，全局队列承担跨 P 分发等工作。实际实现还需要原子操作、全局锁与唤醒协议，不能把“本地队列”理解成完全没有同步成本。

注意：P 不是 CPU 核心，也不只是一个“许可证数字”；G 不是每次运行完就丢弃的函数指针，它还保留栈和执行进度。M 不能凭空制造 CPU 时间，最终仍受 OS 调度与 CPU 配额约束。

GOMAXPROCS=1 允许很多 G 并发推进，但普通 Go 代码同一时刻只有一个执行名额。并发是多个任务可以交错推进，并行是多个任务在同一时刻执行。运行时系统线程、系统调用及某些原生代码的活动不能直接套进“整个进程只运行一个线程”的说法。

固定版本依据：HACKING.md：Gs, Ms, Ps、proc.go 调度器设计注释、GOMAXPROCS 的 API 说明。

02“活着”“能跑”“正在跑”不是一回事

G 的主要状态此刻在做什么排障时意味着什么
_Grunnable可以执行，正在等待调度。如果就绪等待时间持续增加，需要查执行资源与可运行任务的压力。
_Grunning已分配 M 与 P，可以执行 Go 代码。这不承诺对应 M 此刻一定获得物理 CPU，OS 仍可能把线程换下。
_Gwaiting在运行时等待，例如 channel、锁、timer、网络轮询条件。等条件满足才会重新 runnable；加 P 不一定能让条件更快满足。
_Gsyscall处于系统调用路径，关联 M，不执行用户 Go 代码。M 可能被占住；P 可以与它分离。
_Gdead这个 G 对象当前未使用，可能刚退出，也可能准备复用。goroutine 退出不等于其运行时对象必须立刻销毁。

任务放在哪里？

每个 P 有本地运行队列。此版本的环形队列是 [256]guintptr，并另有一个 runnext 槽位。全局运行队列由调度器维护；等待中的 G 则由对应的等待结构记录，不在 runnable 队列里排队消耗 CPU。

runnext 为当前 P 提供下一次优先运行的候选，常用于缩短相关 G 之间的交接延迟。它不是“立即执行”承诺，候选还可能被替换或窃取。在 Go 1.23.4 中，本地环形队列容量为 256；队列满时，runqputslow 将队列前半部分的 128 个 G，连同待入队的 1 个 G，共 129 个 G 转移到全局运行队列。待入队的 G 也可能是被 runnext 替换出来的旧候选，不一定是刚创建的 G。

找任务也不是永远机械执行“本地 → 全局 → 窃取”。findRunnable 会处理 GC、安全点、timer 等条件；还会周期性优先检查全局队列以改善公平性。本版本条件里有 schedtick % 61 == 0，这是实现策略，不是业务可以依赖的调度顺序。

依据：G 状态定义、P 与队列字段、runqput / runqputslow、findRunnable。

04沿一条执行主线，看代码怎样实现

不用一次读完几千行 proc.go。先把“创建 → 找任务 → 执行 → 停下 → 再调度”串起来，然后按场景展开。以下带行号的代码是固定版本原文节选；省略处会分成独立片段。中文伪代码明确标注，不可当作原实现编译。

4.1 数据结构：把任务、线程、执行资源分别保存

g 的 stack 表示栈范围，sched 保存恢复执行所需的上下文，atomicstatus 保存状态。m 持有 curg、g0、p 等关联；p 持有自己的队列。它们是相互引用的运行时对象，不是三个独立工作的“调度线程”。

g0 为什么出现？每个 M 有自己的系统栈，调度器的一部分工作在这里完成。mcall 保存当前 G 的执行位置并转到 g0；等选好下一项工作，再用 gogo 恢复目标 G 的上下文。可把它理解为“先把工单进度收好，再到调度台挑下一张”，但真实实现依赖寄存器、栈指针与架构相关汇编。

g / m / p 定义 · amd64：gogo 与 mcall · 系统栈说明

4.2 创建：go f() 不承诺 f 立刻执行

go f()编译器接入 →newproc→newproc1→runqput→wakep

① newproc1 从空闲 G 中复用对象，必要时分配，准备栈与入口，把它设成 runnable。② runqput(pp, newg, true) 尝试把它放入当前 P 的 runnext；已有候选可能被挤入普通队列。③ wakep 在需要且有资源时唤醒工作线程，不是每创建一个 G 就创建一个 M。

调用者随后继续执行与新 G 得到执行，是两个不同事件。因此 go f(); g() 中，不能仅凭书写顺序推断 f 与 g 的业务先后。

4.4 挂起与唤醒：停的是 G，未必是 M

gopark→mcall(park_m)→running → waiting→schedule

实际代码在转状态前后还处理跟踪与解锁回调。核心含义是：把当前 G 从 M 的当前任务位置卸下，登记在相应等待结构里，再调度其他任务。普通 channel 等待不要求把这个 P 交给另一个线程。

条件满足后，相关代码通过 goready / ready 等路径把 G 变成 runnable 并安排入队。ready 不等于立即 running。还要等一个持有 P 的 M 选择它。

网络等待复用了这个思想：netpollblock 在需要等待时调用 gopark；事件到来后由网络轮询相关路径让任务就绪。CPU 不会持续执行这个 G 去“盯着网络”。线程层面在无工作时也可能阻塞于事件等待，这与“每条连接一个阻塞线程”不同。

gopark · park_m · ready · netpollblock

4.5 系统调用：M 被占用，P 还可以继续服务其他 G

以被运行时标注的 syscall 路径为例，reentersyscall 先保存栈指针、程序位置，把 G 改为 _Gsyscall；M 和 P 分离，P 标为 _Psyscall，为快速返回保留关联线索。

这不等于“任何 syscall 一进入，就立刻新建 M 并完成 P 转交”。普通入口允许快速返回后重取原 P；sysmon → retake 会在条件合适时回收 syscall 中的 P。带已知阻塞提示的 entersyscallblock 则走更积极的交接路径。

返回时 exitsyscallfast 尝试拿回原 P 或空闲 P。成功就能继续；不成功就转慢路径，使 G 重新等待调度，当前 M 也可能停下来。G 可以稍后在另一个 M 上继续运行，普通业务代码不应依赖线程身份。

系统调用多时“线程数比 GOMAXPROCS 大”本身不矛盾。需要继续判断调用是不是该阻塞、并发是不是失控。LockOSThread、cgo 回调等路径涉及线程绑定等特殊规则，需要分别确认其调度行为。

reentersyscall · entersyscallblock · retake · exitsyscall

4.6 工作窃取：移动就绪任务，不抢走正在执行的栈

当自己的工作不足，持有 P 的 M 可以尝试从其他 P 的队列取一批 runnable G。此版本的 runqgrab 通常以大约一半任务为目标；runqsteal 返回其中一个供调用方执行，其余 G 加入窃取方 P 的本地运行队列。真实结果受竞争、队列内容及 runnext 处理影响。

目标 P 怎样选？

stealOrder 用伪随机起点和与 P 总数互质的步长构造遍历顺序。每走一步计算 (当前位置 + 步长) % P总数，使一轮内不重复地覆盖所有 P；stealWork 再跳过当前 P 等不适合的目标。

例如有 6 个 P，起点为 2、步长为 5，得到的序列为：

2→1→0→5→4→3

它不需要先生成一个全局打乱队列。不同 M 可以得到不同的顺序，以分散固定扫描顺序带来的竞争倾向；序列也可能重合，不能据此断言完全没有争用。

Go 1.23.4 的 stealWork 最多尝试 4 轮，找到任务就提前返回。前三轮尝试普通运行队列；最后一轮仍尝试普通队列，并额外允许检查目标 P 的 timer、尝试窃取 runnext。网络轮询在外围调度路径中，不属于“后两轮网络确认”。

stealWork：四轮尝试 · randomOrder / randomEnum：互质步长遍历

这里窃取的是可运行任务，不是把另一个 M 正在运行的 G 从指令中间直接抢过来。窃取成功也不创造 CPU 算力，只改善工作分布。若其他 P 也没有可用任务，调度器会进入更完整的等待与唤醒协议，而不是无休止耗 CPU 找工作。

4.7 自旋与唤醒：找不到工作，为什么不直接睡？

先想一个取舍：M 一旦没任务就休眠，下一个任务到来时又要唤醒线程；一直不睡，又会白白消耗 CPU。Go 让部分工作线程暂时处于 spinning（自旋寻找工作）状态，在有限的寻找过程后再决定是否休眠。

这里的自旋是调度器找工作，与 Mutex 竞争时的短暂自旋是两件事。一个 M 本地没活后，会检查全局任务、非阻塞网络事件等来源；进入自旋寻找阶段时，还会尝试其他 P 的队列、timer 或可用 GC 工作。找到工作就退出自旋，恢复执行；持续没找到，才走释放 P、再次检查、等待事件或休眠的路径。

新工作来了，谁负责叫醒 M？

wakep() 的核心判断是：存在空闲 P，且没有已登记的自旋 M时，才尝试安排一个 M 去工作。如果已经有 M 在找任务，就先依靠它，减少多个线程反复醒来又睡下的开销。取得 P 后，startm 会复用空闲 M，必要时才创建新 M。

但这带来了一个更重要的正确性问题：提交者以为“有人还在找”，寻找者却恰好准备睡下，两边都不再负责唤醒，任务就可能被晾在队列里。为此，运行时对双方的操作顺序作了配合。

这解释了为什么“看一眼队列，空了就睡”不够。退出自旋、工作发布和唤醒之间有竞争窗口，needspinning 等状态还会参与协调。无需记住所有原子指令，但要理解：减少空转是性能策略，防止漏掉工作是正确性要求。

实际排查时，短暂出现 spinning thread 属于正常行为；如果怀疑空转耗 CPU，需要结合 profile、调度摘要和任务负载确认。不能只看到 spinningthreads 非零就认为有异常。

4.8 Netpoller：由谁调用，什么时候调用？

网络事件需要线程去取，但这个线程身份可以变化。Go 不为 Netpoller 固定创建一个永久专职 M；网络轮询由调度路径中的 M 及 sysmon 等路径驱动。

驱动路径何时发生拿到任务以后
findRunnable → netpoll(0)在寻找任务过程中，轮询已初始化、有等待者且相关轮询状态允许时尝试；这次调用不阻塞。可能直接返回一个 G 供当前 M 执行，其余交给任务注入逻辑。
findRunnable → netpoll(delay)工作不足并走到等待路径，M 已释放 P；共享状态协调是否由它进入阻塞轮询，等待时长可受下一次 timer 截止时间限制。返回后尝试取得 P；有 P 时可选任务执行，没有 P 时安排任务入队。
sysmon → netpoll(0)此版本在已初始化、lastpoll != 0 且距记录的轮询时间超过约 10ms 等条件下，补充非阻塞检查。通过 injectglist 注入任务；sysmon 不直接拿 P 执行业务 G。

lastpoll 不只是一个时间记录，零值还参与表示阻塞轮询状态。netpollBreak 则能打断已有轮询，例如等待截止时间需要提前时。由谁进入轮询要经过这些协调，不能简单概括为“最后闲下来的线程负责”。

回到网络请求：G 等待数据时被挂起；某个驱动路径取到平台事件；相关 G 变为 runnable；随后才获得执行。这条链能区分远端等待、事件发现和调度等待。阻塞在轮询里的 M 也不持有 P，因此它不会为了等待网络而占住一个普通 Go 执行名额。

4.9 sysmon：调度体系里的后台监控者

当执行任务的 M 都很忙，或者某个 M 卡在系统调用中，仍需要有运行时路径观察状态并推动系统。sysmon 在独立的 M 上运行，不持有 P；它做监控与协调，不直接承担普通业务 G 的执行。

职责怎么参与边界
长时间执行的抢占请求retake → preemptone 检查调度时间片是否长时间未推进，尝试发出请求。请求可以延后生效；不是每个 G 精确执行 10ms。
回收 syscall 中的 Pretake 按 P 状态、syscall tick、是否有其他工作等条件判断，再尝试回收和交接。并非发现 syscall 就无条件立即回收。
补充网络轮询在前述时间与状态条件下调用非阻塞 netpoll(0)。有阻塞轮询在工作时，会考虑共享的轮询状态。
检查时间触发 GC检查 gcTriggerTime，满足条件时唤醒负责触发 GC 的 goroutine。此版本默认 forcegcperiod 为 2 分钟，还要满足 GC 已启用、当前阶段等条件；不是每两分钟直接执行完整 GC。
配合内存归还与诊断收到相关请求时唤醒 scavenger；按配置输出调度摘要等。scavenger 承担向 OS 归还内存的工作，不能把它与 GC 或 sysmon 本身混为一谈。

常规循环中，sysmon 从约 20μs 的休眠开始，持续空闲时逐步退避，常规退避上限为 10ms。但当所有 P 空闲或 GC 等条件满足时，它还可能进入更长的事件等待。因此这些数字表示检查策略，不构成按固定周期精确运行的保证。

这也解释了为什么 P 都在执行计算时，仍可能出现抢占请求和网络轮询。它们由运行时监控机制推动，最终响应速度仍受平台调度、安全点和运行时状态影响。

4.10 动态栈：栈检查为什么会通向调度器？

goroutine 不必像传统线程那样一开始就准备很大的用户栈。它可以从较小的栈开始，需要更多空间时换到更大的连续栈；在安全的时机，满足条件的栈也可以缩小。一个 G 的内存开销仍然包含栈、运行时对象及其引用的数据，不能按“G 数量 × 2KB”直接估算整个程序内存。

“2KB 起步”需要带上平台条件。在此版本中，stackMin = 2048，实际分配还考虑 stackSystem 与向上取整。本机 Windows 基线额外计入 4096 字节，最小分配向上取整到 8KiB；其他平台的起始值与后续复用策略应按源码核对。

同一条慢路径，处理两种原因

编译器会为需要栈检查的函数生成入口检查；具体比较指令还与架构、栈帧大小和编译优化有关，nosplit 等函数存在例外。正常情况下，stackguard0 是用于检查栈空间的边界值。空间不足时进入 morestack，在 g0 系统栈上调用 newstack。

运行时还会把 stackguard0 设置为特殊值 stackPreempt。这样后续栈检查也会进入慢路径；newstack 识别到它后，知道需要处理的是抢占请求，而不一定真的需要扩栈。

真正扩栈时，newstack 以倍增为基础计算目标大小，必要时继续放大以容纳所需栈帧，再由 copystack 复制内容并修正相关指针。缩栈则要满足安全性、使用量等条件，不会每退出一个函数就立即发生。

同步抢占完成后，G 以后仍能从保存的现场继续。现在就能解释 execute 中的 gp.stackguard0 = gp.stack.lo + stackGuard：它恢复普通栈检查边界，清掉作为本次请求入口的特殊值；后续仍可产生新的抢占请求。

4.11 异步抢占：没有函数调用的计算循环，怎样停下来？

同步栈检查要等程序走到相关检查位置。一个长时间不调用函数的计算循环，可能长时间碰不到这样的机会。Go 1.14 引入异步抢占，使这类循环不再容易拖住调度或显著延迟 GC；具体支持范围以平台与版本为准。

触发线索仍来自 sysmon → retake → preemptone。此版本中，retake 观察同一调度时间片持续过久时请求抢占：

10ms 是监控判定的阈值线索。发起检查、送达通知和找到可安全暂停的位置都需要时间；它不是固定的 G 时间片上限，也不保证定时器或其他任务在 10ms 内运行。

阶段Unix 常见实现Windows 实现
提出请求preemptone 设置抢占相关状态；平台支持且未关闭异步抢占时，调用 preemptM。
获得目标执行现场向目标 M 发送抢占信号，常用 SIGURG；信号处理路径检查目标 G。使用线程句柄挂起目标线程、读取其上下文，再作检查。
判断是否能暂停检查目标是否为用户 G、M 当前状态是否允许、栈空间是否足够，以及 PC 是否处在编译器和运行时认可的异步安全点。
安排进入抢占入口调整信号上下文，使恢复时进入 asyncPreempt。调整并设置线程上下文，再恢复线程。
转入调度asyncPreempt 保存用户寄存器，调用 asyncPreempt2，再按请求进入普通重新调度或特殊暂停路径。

Unix 的“注入”指修改保存的执行上下文，让目标恢复时经过抢占入口，不是修改业务机器码。普通重新调度路径可概括为：

asyncPreempt→asyncPreempt2→mcall(gopreempt_m)→goschedImpl(gp, true)

为什么需要安全点？

暂停后的运行时必须能保存和恢复现场，也要能正确识别栈与寄存器中的指针。停在运行时临界操作、尚未形成一致状态的指令序列或缺少必要元数据的位置，都可能破坏这些要求。因此 isAsyncSafePoint 会过滤不安全的位置，部分可重启序列还会调整恢复 PC。

这里的 mp.locks 等是运行时内部状态，不能理解成“业务代码只要持有 sync.Mutex 就不能被抢占”。持有业务互斥锁的 G 完全可能被换下；其他 G 仍然要等它以后继续执行并释放锁。

安全条件不满足时，这次尝试不会强行切走。请求可能在之后的同步检查或异步机会中得到响应。异步抢占改善可调度性，仍不提供业务优先级、固定轮转顺序或实时延迟保证。

4.12 STW：怎样让所有 P 配合停下来？

GC 在部分阶段切换时需要暂停普通 Go 执行。发起方通过 stopTheWorldWithSema 设置 gcwaiting、初始化 stopwait，并调用 preemptall 请求运行中的 P 配合。接下来根据 P 的状态分别处理：

P 的状态停止方式
发起方当前的 P直接记录为 _Pgcstop，减少停止计数。
空闲 P从空闲列表取出，记录为 _Pgcstop，减少停止计数。
系统调用中的 P尝试 CAS：_Psyscall → _Pgcstop。P 已与 M 脱离，不必等 M 的系统调用返回。
正在运行的 P经抢占或其他调度机会观察到 gcwaiting，典型路径进入 gcstopm，释放 P、记录停止并减少计数。

对于运行中的 G，一条普通响应路径是 preemptone → gopreempt_m / goschedImpl → schedule / findRunnable → gcstopm。G 可以先回到 runnable，而 P 随后停止。全局 STW 不会统一设置所有 G 的 preemptStop，再让它们全部经过 preemptPark；后者主要用于 suspendG 暂停指定 G 等路径。

需要等待的 P 尚未全部停下时，发起方等待停止通知，并按实现策略重复提出抢占请求。处于运行时暂不允许抢占的区域，可能拉长停止确认阶段；正常 cgo 调用则可以与 P 脱离，不能把 cgo 执行时间直接等同于 STW 等待时间。

指标测量范围

/sched/pauses/total/gc:seconds从决定停止世界，到恢复世界，包含前面的停止确认阶段。

4.13 Gosched：主动让出，但仍然可以运行

runtime.Gosched() 让当前 G 暂时交出执行机会。它没有等待某个条件，因此 G 会从 running 变为 runnable，以后无需另一方专门唤醒就能继续。

runtime.Gosched()→mcall(gosched_m)→goschedImpl(gp, false)

在此版本的 goschedImpl 中，运行时把 G 改成 runnable，解除当前 M 与 G 的执行关联，将 G 放进全局运行队列，必要时尝试唤醒 M，然后调用 schedule 找下一项工作。这个 G 将来被选中后，从 Gosched() 调用后面继续。

动作G 停下后的状态怎样继续
runtime.Gosched()runnable等待调度器再次选择；没有业务条件需要满足。
尚不能完成的 channel 操作waiting相应通信、关闭等事件使它就绪，再等待调度。
time.Sleep(d)，d > 0等待 timer定时条件满足后就绪；不能保证恰好在 d 后开始执行。
普通抢占后的重新调度通常回到 runnable运行时发起而非业务主动调用；特殊暂停请求另有路径。

放进全局队列会改变当前 G 再次参与选择的位置，但不保证某个其他 G 一定先执行；没有其他可执行任务时，当前 G 也可以很快回来。它既不表示“暂停固定时长”，也不能充当限流或同步协议。

例如 for !ready { runtime.Gosched() } 仍然在反复检查条件；如果 ready 是无同步的共享变量，还可能存在数据竞争。确实要等事件，应使用 channel、条件变量或其他合适的同步。把 Gosched 用作调度实验的观察入口，比把它当成常规修复手段更合适。

怎样在 trace 中确认？

分别运行下面的命令，逐个打开两份轨迹：

go tool trace preempt.trace
go tool trace preempt-off.trace
  1. 定位执行 burn 的主 G，以及 time.AfterFunc 创建的回调 G，对齐计算开始、回调执行和计算结束的位置。
  2. 在默认配置的轨迹中，观察计算循环结束前是否出现主 G 的 Running → Runnable 抢占，再看回调 G 何时获得 P 并开始执行。
  3. 在对照轨迹中，观察主 G 连续计算的区间，以及回调是否推迟到循环结束附近。以实际轨迹为准，不预设抢占必然发生在 10ms，也不预设回调就绪后立即运行。

需要查看文本事件和关联调用栈时，可以分别执行：

go tool trace -d=1 preempt.trace
go tool trace -d=1 preempt-off.trace

这不表示所有回调都能在 10ms 左右得到执行。采样、OS 调度、机器负载和具体代码都会影响结果。asyncpreemptoff 只关闭异步抢占，同步安全点仍然存在，因此对照 trace 也可能出现抢占事件；应结合事件位置、调用栈与回调时刻判断。

trace 里看什么？

  1. 打开实验 A 的 trace，寻找 worker 的等待、唤醒和再次运行；关注 timer/sleep、channel 与同步相关的状态变化。
  2. 把一个 G 的 waiting → runnable 与 runnable → running 分开看。前者是条件满足，后者才是获得执行机会。
  3. 查看调度延迟（scheduler latency）与时间线，判断“就绪后等了多久”。需要时导出调度延迟 profile；它与 CPU 热点 profile 回答的问题不同。
go tool trace -pprof=sched wait.trace > sched.pprof
go tool pprof sched.pprof

上面的二进制重定向在 PowerShell 7.4+、cmd 或 POSIX shell 下使用；旧 Windows PowerShell 应避免以文本方式重定向 profile。阅读 trace 的输出格式可能随 Go 版本变化。

func burn(n uint64) uint64 {
	x := uint64(0x123456789abcdef)
	for i := uint64(0); i < n; i++ {
		x ^= x << 13
		x ^= x >> 7
		x ^= x << 17
	}
	return x
}

func cpu(workers int) (time.Duration, uint64) {
	const tasks = 8
	jobs := make(chan struct{}, tasks)
	results := make(chan uint64, tasks)
	for i := 0; i < tasks; i++ {
		jobs <- struct{}{}
	}
	close(jobs)
	start := time.Now()
	for i := 0; i < workers; i++ {
		go func() {
			for range jobs {
				results <- burn(8_000_000)
			}
		}()
	}
	var sum uint64
	for i := 0; i < tasks; i++ {
		sum += <-results
	}
	return time.Since(start), sum
}

		ready.Add(n)
		done.Add(n)
		for i := 0; i < n; i++ {
			go func() {
				defer done.Done()
				ready.Done()
				<-start
				time.Sleep(80 * time.Millisecond)
			}()
		}
		ready.Wait()
		peak := runtime.NumGoroutine()
		begin := time.Now()
		close(start)
		done.Wait()
		fmt.Printf("wait tasks=%d sleep=80ms elapsed=%v live-before-release=%d\n", n, time.Since(begin).Round(time.Microsecond), peak)
	case "cpu":
		_, _ = cpu(1) // warm-up
		for _, workers := range []int{1, 8} {
			times := make([]time.Duration, 3)
			var sum uint64
			for i := range times {
				times[i], sum = cpu(workers)
			}
			sort.Slice(times, func(i, j int) bool { return times[i] < times[j] })
			fmt.Printf("cpu tasks=8 workers=%d total-iterations=64000000 median=%v checksum=%d samples=%v\n", workers, times[1].Round(time.Microsecond), sum, times)
		}
	case "yield":
		var wg sync.WaitGroup
		wg.Add(2)
		for id := 1; id <= 2; id++ {
			id := id
			go func() {
				defer wg.Done()
				for turn := 1; turn <= 2; turn++ {
					fmt.Printf("yield worker=%d turn=%d before\n", id, turn)
					runtime.Gosched()
					fmt.Printf("yield worker=%d turn=%d after\n", id, turn)
				}
			}()
		}
		wg.Wait()
	case "preempt":
		begin := time.Now()
		timerDone := make(chan struct{})
		time.AfterFunc(10*time.Millisecond, func() {
			fmt.Printf("preempt timer-delay=%v\n", time.Since(begin).Round(time.Microsecond))
			close(timerDone)
		})
		sum := burn(160_000_000) // loop body has no function call
		fmt.Printf("preempt cpu-finished=%v checksum=%d\n", time.Since(begin).Round(time.Microsecond), sum)
		<-timerDone
	default:
		panic("unknown mode")
	}
}

06把原理变成一次实际排查

结合真实案例：取证命令、证据边界与修复验证 →

假设某个任务处理程序变慢了，不必先背调度源码。先问：它是在做计算、等执行机会，还是等外部条件？下面按证据继续缩小范围。

看到的证据可以形成的假设下一项验证 / 行动
CPU profile 中业务计算占主导，可用 CPU 接近饱和计算量、算法或分配等在消耗执行资源。先优化热点；用固定工作量比较 worker 数。并发控制可以减少争抢，不能替代计算本身。
trace 中 runnable 等待增加任务已经能跑，但迟迟没获得执行；可能是负载过高、资源配额、GC 竞争等。关联 P 使用、GC 时间线与 OS/容器指标；不能单凭这一项宣布“调度器有 bug”。
CPU 不高，堆栈集中在 channel 或同步等待可能是生产消费不平衡、持锁过久、等待条件不能满足。沿等待链查谁负责推进；看 block/mutex profile。增加 GOMAXPROCS 未必有帮助。
大量 I/O wait，且外部请求耗时增加瓶颈可能在远端或网络；G 被正确挂起并不让远端变快。核对超时、取消、外部容量与调用并发；控制在途任务，避免把等待变成无界积压。
线程增长，并伴随 syscall/cgo 活动部分 M 被外部调用占用，运行时可能启用其他 M。关联 threadcreate、goroutine 栈与原生库指标；限制该类调用并发，继续确认是否存在泄漏。
CPU 配额被节流，延迟与节流时间相关OS/容器不给足够 CPU 时间，不能只在 Go 队列内部找原因。核对工具链版本、实际 GOMAXPROCS、手工覆盖及 CPU 配额；依据负载调整后再测。

值得熟悉的三个入口

执行轨迹：用 runtime/trace 在有限时间内采集，观察 G 的等待、就绪、执行与抢占。

调度摘要：先构建程序，再给运行的二进制设置 GODEBUG。以下命令使用实验程序；排查实际负载时替换为对应程序与参数。

# PowerShell：运行后恢复原来的 GODEBUG
$previousDebug = $env:GODEBUG
try {
    $env:GODEBUG = "schedtrace=1000"
    .\gmp-lab.exe -mode cpu
} finally {
    $env:GODEBUG = $previousDebug
}

# POSIX Shell / Git Bash / Linux / macOS：只作用于这次运行
GODEBUG=schedtrace=1000 ./gmp-lab -mode cpu

# Windows cmd：只修改子进程环境
cmd /c "set GODEBUG=schedtrace=1000&& gmp-lab.exe -mode cpu"

竞态检测：检查测试实际执行路径上的数据竞争。

go test -race ./...

schedtrace=1000 表示约每 1000ms 输出调度摘要。示例程序很短，可能只看到启动附近的一条；要持续观察应选择运行更久的实际负载。摘要中的线程数、空闲 P、全局队列与各本地队列长度都是线索，不是单项故障判据。-race 检查数据竞争，不保证发现所有业务竞态、死锁或泄漏。

版本差异直接影响建议：Go 1.23.4 默认并行度不具备 Go 1.25 引入的容器 CPU 带宽配额感知行为。Go 1.25 引入新默认值和更新机制，但具体仍受平台、模块语言版本兼容设置、环境变量及显式 GOMAXPROCS 调用影响。先确认实际生效值，再讨论是否覆盖；不要无条件照搬旧的容器调优教程。

依据：GODEBUG / schedtrace 文档、Race Detector、官方容器并行度说明、Go 1.25 runtime 版本说明。

07资深开发者，学到哪一层最划算？

  • 必须能解释：G、M、P 的区别；runnable 与 waiting；并发与并行；为什么 GOMAXPROCS 不是线程数或 goroutine 数上限。
  • 必须能判断：channel 等待、网络轮询与阻塞系统调用的差别；为什么加 worker、加 P 或引入协程池都需要前提。
  • 必须能取证：用 profile 找计算与等待热点，用 trace 查看就绪到执行的过程；用同步原语保证顺序，用 race detector 辅助发现问题；能区分 Gosched 的主动让出与条件等待。
  • 值得会读：newproc、schedule / findRunnable、park / ready、syscall 交接、stealWork、自旋与唤醒、netpoll、sysmon、两类抢占路径以及 STW 停止确认与恢复路径。遇到具体问题时，能沿固定版本源码查到边界。
  • 按需深挖：汇编的逐条寄存器操作、唤醒协议的全部竞争窗口、各平台信号/线程细节。除非排查 runtime、cgo 或极端性能问题，不必先把这些背下来。

一个 G 得到 CPU，需要经过条件已满足 → 进入可运行状态 → 被持有 P 的 M 选中 → M 获得 OS 执行时间。排查耗时时，要区分延迟发生在哪一段。
