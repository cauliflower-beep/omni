# 大模型应用开发的分阶段学习路线

## 时间与推进规则

每周 12 小时：读文档 3 小时、实现与实验 7 小时、复盘 2 小时。24 周约 288 小时；每周 6 小时可延长至约 48 周。

准备知识：基本编程、HTTP、Git、数据库。实现可选 Python/LangGraph 或 Go/Eino。

实验流程：任务定义 → 基线 → 失败分析 → 单变量改动 → 评估。各阶段阈值为学习验收目标，指标定义见[评估标准](evaluation.md)。

| 阶段 | 建议周数 | 工作量 | 核心交付 | 过关重点 |
| --- | --- | --- | --- | --- |
| 0 基础与环境 | 第 1 周 | 12 小时 | 场景说明、环境记录、首个 API 实验 | 能解释输入输出与失败 |
| 1 模型接口与结构化 | 第 2 至 3 周 | 24 小时 | 模型接口服务、工单抽取实验 | 有业务校验、取消和类型边界 |
| 2 评估与上下文 | 第 4 至 6 周 | 36 小时 | 数据集、评估器、两版对照报告 | 改动有证据，有留出集 |
| 3 RAG 与数据生命周期 | 第 7 至 10 周 | 48 小时 | 带引用的文档助手 | 检索、生成、权限分别验收 |
| 4 工具调用与 Agent | 第 11 至 14 周 | 48 小时 | 可中断、可审批的任务助手 | 业务状态正确，执行受控 |
| 5 运行与交付 | 第 15 至 18 周 | 48 小时 | 部署、链路、故障与成本报告 | 失败可定位、恢复和回滚 |
| 6 完整项目与源码改造 | 第 19 至 22 周 | 48 小时 | 主项目正式演示版、样本改造 | 场景闭环与个人贡献清楚 |
| 7 求职与能力校准 | 第 23 至 24 周 | 24 小时 | 作品集、岗位映射、系统设计讲解 | 能说明取舍、指标和局限 |

## 阶段 0 基础与环境

**目标**：从 AI 应用基础开始，建立可运行、可观察的小实验，理解一次模型请求的输入、输出和失败路径。

学习 Token、上下文、消息角色、训练与推理、Embedding、采样参数、幻觉，以及普通文本接口、结构化输出和工具调用的区别。Transformer 先理解信息如何在上下文中关联，不要求本周训练模型。参考[微软入门课程](https://github.com/microsoft/generative-ai-for-beginners)中的概念、Prompt 和应用生命周期主题，配合 [Hugging Face 第一章](https://huggingface.co/learn/llm-course/chapter1/1)。

动手任务：

1. 写一页场景定义：用户是谁、现在怎么做、希望节省什么、哪些答案或动作不能错。可从技术文档知识助手开始。
2. 准备 20 条实际问题，标出已知答案、查不到时的行为和可用来源。
3. 检查所选语言、Git、容器运行环境和磁盘内存；Windows 可按需使用 WSL2。按选用 SDK 的实际要求安装版本，把版本写入记录；命令存在不代表服务可用。
4. 选择一个当前账号与地区可用的模型服务，确认文本、流式、工具、结构化、Embedding 等分别是否支持。不要求先买显卡。
5. 用 Python 或 Go 发送一次最小请求，记录耗时、返回类型、usage；再制造一次错误 API Key 或超时，观察错误路径。
6. 用所选语言读取一份 JSONL、批量调用接口并写出结果，学习当前任务需要的类型和异常处理。

**交付**：场景说明、环境版本表、20 条问题、正常与失败两份脱敏记录。

**验收**：能够解释一次请求的完整路径、为什么可能答错、费用来自哪里；能重跑成功和失败实验。实际密钥不进入仓库。

## 阶段 1 模型接口与结构化输出

**目标**：使用 Python 或 Go 做出可以接入业务的最小服务，掌握供应商接口，而非只有聊天演示。

学习消息与响应类型、流式事件、JSON Schema、拒绝/截断/超时、usage、限流与重试。调用原生接口时保留供应商语义；“OpenAI 兼容”不能自动推导为 Responses、工具流式和严格 Schema 都兼容。[结构化输出](https://developers.openai.com/api/docs/guides/structured-outputs)、[DeepSeek 接口](https://api-docs.deepseek.com/)

动手任务：

1. 用 HTTP 框架提供文本生成与流式响应接口，贯穿请求取消信号；Go 可使用 `context.Context`，Python 路径需处理异步任务取消，客户端取消后终止上游工作。
2. 做“工单抽取”：输入问题描述，输出分类、紧急程度、订单号、缺失字段。未提供的订单号必须标为空或缺失，不猜测。
3. 建立供应商适配边界：支持的功能、模型标识、参数、响应事件和错误保留清楚；先接一家，再用第二家小范围验证切换。
4. 对完整响应做业务校验。Schema 只约束结构，仍检查枚举业务含义、日期范围和引用是否真实存在。
5. 对适合重试的网络错误/限流做有上限的退避；不对任意失败无限重试。写操作尚不接入。

**交付**：模型接口服务、脱敏配置示例、接口说明、能力矩阵、30 条结构化用例，以及可重复运行的批量调用脚本；使用所选语言实现即可。

**验收**：30 条用例全部得到可判定的状态；成功结构均能被程序消费，拒绝、超时、截断进入独立错误路径；取消和限流场景可复现。此阶段不以“抽取内容 100% 正确”为要求，错误进入下一阶段数据集。

## 阶段 2 评估与上下文工程

**目标**：能解释“这次改 Prompt 到底改善了什么”，建立后续全部阶段共用的评估方法。

学习少样本示例、上下文筛选与压缩、问题澄清、评估集划分、确定性校验、人工评分、LLM Judge 的偏差。阅读 [Anthropic 上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)和 [2026 Agent 评估指南](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)。

动手任务：

1. 将工单数据扩充为 100 条：60 条开发、20 条验证、20 条留出。按模板来源或原始事件分组，避免同一条改写后跨集合。
2. 覆盖正常输入、口语、缺失信息、冲突信息、超长输入和注入文本。合成数据标记来源，经人工核对后加入。
3. 为分类做精确匹配，为抽取做字段评分；对解释质量写简明评分规则。至少人工复核 20 条及全部重大失败。
4. 固定模型配置，比较两个 Prompt；再固定 Prompt 比较两个模型。记录质量、耗时和费用，不同时更改多个变量。
5. 建立可重复运行的评估命令，输出逐例记录和汇总。可以用 Python 自有脚本，或选择 [Promptfoo](https://www.promptfoo.dev/docs/intro/)；不同时引入多套工具。
6. 给一次失败做归因：任务定义、输入、提示、模型能力、业务规则还是接口处理。

**交付**：版本化数据集、评分规则、评估脚本、至少两份有基线的对照报告和错误分类。

**验收**：留出集关键字段 Micro-F1 建议达到 0.90；没有提供的标识不得被捏造；Schema 通过率和业务正确率分开报告。冻结留出集后不针对其逐题调参；若用于分析，则转入开发集并补新留出样本。模型判分必须与人工核查对照。

## 阶段 3 RAG 与数据生命周期

**目标**：让模型基于可追溯的业务资料回答，能区分“没检索到”和“检索到了却答错”。

学习加载/解析、分块、Embedding、关键词检索、向量召回、混合检索与重排，随后加入引用、版本、删除、权限和缓存。先精读 [RAG 原论文摘要与方法概览](https://arxiv.org/abs/2005.11401)，再用 [pgvector](https://github.com/pgvector/pgvector)做最小实验；不把论文中的联合训练当成应用必需步骤。

动手任务：

1. 选择 30 至 50 份有明确来源与版本的技术文档，保留文档、章节、来源、版本和更新时间。
2. 建立可恢复的索引任务：文件哈希、解析状态、chunk ID、Embedding 模型与维度；同一版本重复上传不会重复入库。
3. 建立 100 条独立的问答评估：60 条开发、40 条留出；留出中 30 条可回答、10 条资料缺失/冲突/版本边界问题。另设跨租户安全用例。
4. 比较关键词、向量、混合三种检索；先检查召回，再尝试重排。英文标识符、函数名、错误码保留精确检索路径。Postgres 默认全文分词的中文效果需要单独验证。
5. 生成答案必须返回可定位的证据；没有依据时说明缺失，冲突版本时先区分适用范围。
6. 更新或删除文档，验证旧索引、答案缓存、引用与原文访问同步处理。权限过滤在检索时执行，下载原文时再次校验。
7. 从 WeKnora 或 Dify 中选择一个固定快照，阅读服务入口、接口、索引与检索模块；写出与练习实现的差异。

**交付**：带 UI 或清晰 API 的知识助手、索引管理、三种检索对照、引用和权限实验。

**验收**：30 条可回答留出问题的 Evidence Hit@5 至少 27/30；人工业务通过至少 24/30；引用支撑率至少 90%；10 条边界问题中至少 9 条正确拒答或澄清。另测两个租户至少 20 个交叉访问，检索结果、答案和原文下载均不得泄漏。分母和评分口径见[评估标准](evaluation.md)。

## 阶段 4 工具调用与受控 Agent

**目标**：使系统能够在限定范围内查数据、提方案和执行被批准的动作。

先手写一遍“模型提出调用 → 校验 → 执行 → 返回结果 → 决定结束或继续”的循环，再选择 Python/LangGraph 或 Go/Eino 表达同一流程。读[工具调用官方说明](https://developers.openai.com/api/docs/guides/function-calling)、[LangGraph](https://docs.langchain.com/oss/python/langgraph/overview)、[Eino](https://www.cloudwego.io/docs/eino/overview/)和 [Agent 工程模式](https://www.anthropic.com/research/building-effective-agents)。

动手任务：

1. 从 3 个只读工具开始：查文档、查模拟服务状态、查模拟指标。工具参数明确、结果带来源、错误可识别。
2. 对比固定 Workflow 与动态 Agent，用同一任务集判断是否值得增加自主决策。
3. 加入最大步数、单工具超时、总时限、Token/费用上限、取消和状态持久化，防止循环失控。
4. 增加一个模拟写操作，如生成或创建内部工单：展示待执行参数，人确认后由服务端检查授权、版本和幂等键再执行。
5. 用所选框架实现“暂停 → 恢复”，验证检查点与状态恢复语义。
6. 使用所选语言对应的 MCP SDK 暴露一个只读知识工具，并通过两个兼容客户端验证；Go 路径可参考[官方 Go MCP SDK](https://github.com/modelcontextprotocol/go-sdk)。记录双方协议版本。当前规范入口为 [2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28)，旧教程的握手或会话假设不可直接照搬。
7. 测试工具返回的恶意指令、越权资源、错误工具参数和重复调用；不能让检索文本获得系统权限。

**交付**：工具契约、可恢复任务服务、只读 MCP Server、审批 UI/接口、Workflow 与 Agent 对照报告。

**验收**：准备 40 个任务，其中 20 开发、20 留出；留出每题独立重置环境跑 3 次，共 60 次，业务成功至少 48/60，并报告每题分布。至少 10 个越权/注入用例没有未授权副作用；重复确认与失败重试不重复写入。验收查最终数据库/业务状态，不能只看模型说“完成”。

## 阶段 5 运行与交付

**目标**：在可说明的资源和预算下运行，遇到失败能定位、控制影响和恢复。

学习请求/任务分离、流式背压、并发限制、队列、缓存隔离、Trace、模型费用、数据脱敏和评估回归。安全案例参考 [OWASP LLM 风险](https://genai.owasp.org/llm-top-10/)，观测可选 [Langfuse](https://docs.langfuse.com/)；Go 优先走 OpenTelemetry 兼容路径，核对接收端要求。

动手任务：

1. 为主项目增加一条命令启动、健康检查、迁移、持久化目录、备份恢复和回滚说明，固定依赖与镜像版本。
2. 全链路记录 request/run ID、模型与 Prompt 版本、检索与工具耗时、usage、结束原因；敏感正文按需脱敏与采样。
3. 注入上游 429/5xx、长延迟、断流、队列重复投递、进程重启和客户端取消。
4. 用模拟供应商测试 1/5/20 并发；真实接口小规模验证外部限制。分别报告容量和供应商配额，不能用模拟吞吐宣称真实模型吞吐。
5. 建议先设用户体验目标为首 Token p95 不超过 5 秒、简单问答总耗时 p95 不超过 20 秒；固定问题长度、模型、并发和网络条件后验证，达不到要分析并重定目标。
6. 对每 100 次成功任务统计包括失败、重试、Embedding、重排和评估在内的费用。设一个明确的实验预算硬上限。
7. 将核心确定性测试与小型评估冒烟集接入 CI，完整评估按变更或发布触发；升级模型/Prompt/索引都做对照。

**交付**：部署说明、可观测面板或报告、故障矩阵、压测与成本报告、回滚记录。

**验收**：每种故障都有可识别状态及恢复方式；恢复后的写任务不重复生效；能通过 trace 定位一次检索失败和一次工具失败；5 并发、100 次固定请求的失败率与 p95 完整报告；不达体验目标的原因与下一步清楚。负载和 SLO 是学习试验，不代表生产承诺。

## 阶段 6 完整项目与开源样本改造

**目标**：形成能让别人试用、能解释个人贡献的作品。

从[项目方案](projects.md)选主项目，优先完成知识助手；按兴趣选择运维 Agent 或文档工单流程做第二个较小项目。开源样本最多选一个深读、一个比较，避免同时部署四套平台。

动手任务：在自己的项目或合法使用的样本上完成一个真实改动，例如新数据连接器、版本过滤、可恢复索引、审批节点或检索评估；保存前后差异和回归结果。邀请 3 至 5 位实际试用者完成固定任务，收集至少 20 次任务反馈；用户难以邀请时，记录这一限制，先用未参与开发的人进行盲测。

**交付**：可重现部署、脱敏演示数据、架构图、效果/成本报告、失败案例、变更说明和 5 至 10 分钟演示。源码改动可以保持本地，不以 PR 被合并作为完成条件。

**验收**：另一位开发者能按说明启动并完成 5 个固定演示任务；展示一次失败、一次恢复、一次改进对照。能指出借用的开源部分与自己增加的部分，实际试用数据与人工构造数据分开。

## 阶段 7 求职与能力校准

**目标**：将工程事实转成岗位能理解的证据。

收集目标地区 15 至 20 个官方 JD 并做能力映射，准备主项目讲解、一次 RAG 系统设计、一次工具执行与权限设计、一次效果退化排查。继续练习所选语言的并发与异步、数据库、网络和系统设计基础。

准备回答：为什么这个场景需要模型？为什么用 RAG 而不是全文塞入上下文？如何知道召回失败？为什么不先做微调或多 Agent？如何防止重复执行？单次成功任务费用如何计算？换模型后怎样判断可以发布？

**交付**：简历项目段落、架构与指标附件、岗位映射、两轮模拟面试复盘。

**验收**：能在 10 分钟内讲清场景、基线、方案、关键失败、实测指标和个人贡献；简历里的每个数字都能定位到实验记录，未知数据不填估计值。

## 前两周的具体安排

每次约 2 小时，每周六次；可以按个人作息合并。无需等待读完全部资料。

| 次数 | 第 1 周 | 第 2 周 |
| --- | --- | --- |
| 1 | 场景与 20 条问题 | 文本接口与错误类型 |
| 2 | Token/上下文/训练推理，检查环境 | 流式响应与客户端取消 |
| 3 | 正常请求，记录 usage 与耗时 | 定义工单 Schema 和业务校验 |
| 4 | 超时、错误凭证、限流的观察 | 跑 30 条用例，登记错误 |
| 5 | JSONL 与批量请求 | Prompt 示例与缺失字段处理 |
| 6 | 重跑、写记录、说明概念边界 | 补接口说明和供应商能力矩阵 |

第 3 周继续完善阶段 1；第 4 周再开始系统评估。若第 1 周 API、网络或 Docker 受阻，可以先用本地假响应验证接口和评估器，但必须把模拟结果与真实模型结果分开。

## 何时进入选修分支

| 触发条件 | 才增加的内容 | 追加练习与验收 |
| --- | --- | --- |
| 项目或岗位需要另一种实现语言 | Python 或 Go 的另一条实现路径 | 将一个已有任务迁移，保持同一评估集验证 |
| 私有部署或调用量使 API 不合适 | vLLM、量化与推理观测 | 自托管一个模型，对比资源、吞吐、质量与总成本 |
| 固定任务持续失败，已有足量合规标注 | LoRA/SFT 和数据治理 | 与最佳 Prompt/RAG 基线做留出集对照，给出数据和训练成本 |
| 单 Agent 在可拆任务上存在明确瓶颈 | 多 Agent 协作 | 与单 Agent 同预算对照，验证收益超过协调成本 |
| 业务依赖图像、表格或语音 | 多模态解析或实时交互 | 建立该模态独立数据集与失败分类，再纳入主链路 |

选修建议另留 2 至 6 周做最小实验，具体以硬件、数据和目标岗位为准，不挤掉核心阶段的评估与交付。
