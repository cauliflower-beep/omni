并发与 CPU：五个服务变慢的真实案例

00先分清：任务有多少，能并行多少，CPU 给多少

增加 worker、提高 GOMAXPROCS、调整容器 CPU，改变的是不同的量。下面五个案例分别遇到了CPU 节流、锁交接、执行并行度下降、前后台资源争用和调度开销；相似的“服务变慢”，需要不同的证据。

量控制什么不会自动获得什么
业务并发度同时进入某段处理流程的任务数；可用 worker、信号量或准入队列限制。更多 CPU 时间；更快的数据库、锁或下游。
GOMAXPROCSP 的数量；约束同时执行普通 Go 代码的并行度。独占的物理核心；整个进程的线程数上限。
CPU 带宽配额cgroup 在一段周期内允许使用的累计 CPU 时间。对等数量的专属核心；进程内部的业务优先级。

可以把它们分别想成“接了多少单”“开了多少工作台”“每天获准使用多少工时”。多接单、多开工作台，都可能只是增加排队和争抢。回到准确含义：等待中的 G 不等于可运行的 G；P 也不等于 CPU 核心。

案例最值得追问的现象关键证据
Uber 负载均衡器P 增加，吞吐下降，长尾延迟上升。GOMAXPROCS 对照测试、cgroup 节流计数。
HTTP/RPC 锁竞争参与计算和争锁的并发度只增加一点，吞吐却骤降。并发度扫描、trace 中的锁交接时间。
Grab Kafka → S3CPU 配置跨过整数边界后，消费积压。VPA 时间线、有效 P 数与消费速率。
CockroachDB 备份后台工作运行时，在线查询变慢。请求追踪、runnable → running 的延迟。
UDP 流媒体服务相同业务负载，升级工具链后 CPU 增加。交叉编译对照、CPU profile、schedtrace。

每节的“原始记录”是来源摘要；“迁移到自己的服务”是本文补充的排查建议。原帖数据、作者假设与本文示意分别标明；本页没有把历史案例重新运行为本机实验。原理见 G、M、P；取证工具见 Go 官方诊断指南。

01Uber：P 增加了，CPU 时间却没有增加

来源：uber-go/automaxprocs · Performance。真实内部负载均衡器的对照测试；README 未注明该组数据的 Go 版本、测试日期及完整压测配置。

1.1 原始记录：2 核配额下的六组结果

Uber 固定 CPU 配额为 200%（相当于 2 核的 CPU 时间预算），改变 GOMAXPROCS。P=2 时吞吐最高；继续加 P，P50 虽然降低，吞吐和长尾延迟却变差。原作者还检查了 cpu.stat，并报告：调低到与配额匹配后，这次测试中未再观察到 CPU 节流。

1.2 为什么会这样：并行度与带宽是两种限制

GOMAXPROCS 允许更多普通 Go 代码同时执行；cgroup 配额限制这些执行累计能用多久。假设一个周期为 100ms、配额为 200ms CPU 时间：理论上，2 个线程各执行 100ms，或 8 个线程各执行 25ms，都能耗尽同一笔预算。后一种方式可能更早耗尽配额，随后等待补充。

这是理想化预算示意：忽略其他线程、内核细节、CPU 竞争与 burst 配置，不是 Uber 的原始时间线。它解释了为什么“短时间跑得更并行”与“持续吞吐更高”不能画等号。调度器即使有 runnable G，也不能替操作系统突破 CPU 带宽限制。

机制依据：Linux CFS Bandwidth Control。GOMAXPROCS 的限制针对普通 Go 代码，cgroup 预算还会受到同组其他执行活动影响。

1.3 迁移到自己的服务：怎样确认是配额问题？

  1. 先取实际值。记录运行中进程的 Go 版本、GOMAXPROCS、容器 CPU limit 及 cpuset；不要把宿主机 NumCPU 当成容器可持续使用的 CPU 带宽。
  2. 看节流的时间变化。读取目标 cgroup 的 cpu.stat，对比固定窗口内节流次数与节流时间的增量，并与 P99、吞吐对齐。累计值很大，只能说明过去发生过节流。
  3. 做单变量对照。保持流量模型、CPU limit、实例数和请求内容一致，逐档改变 P；同时记录成功 RPS、超时、P50/P99 和 CPU 秒/请求。不要一边扩容一边改 P，再归因于其中一项。

若节流与延迟上升同步，降低 P 后节流和长尾改善，才形成较完整的证据。也可能需要增加配额或减少计算量。P=1 的 P99.9 更低，但吞吐也更低，最终选择由吞吐目标和延迟目标共同决定。

版本边界：Go 1.25 引入 Linux 容器 CPU 带宽感知和默认值更新机制。实际行为受工具链、模块语言版本、GODEBUG、GOMAXPROCS 环境变量和显式 API 调用影响。先确认生效配置；不能直接推导“每个 Go 容器都该安装 automaxprocs”或“P 永远等于 CPU limit”。官方说明

回到原理：P 与 CPU 的区别 · 实际命令：检查 cgroup

02RPC：短临界区，也可能把服务拖进拥塞

来源：golang/go #33747，2019-08。线上 HTTP/RPC 服务的观察，加上独立微基准；测试版本为 Go 1.8.7、1.9.7、1.12.7、1.13beta1。

2.1 原始记录：只多一个并发参与者，吞吐却大幅下降

报告者的服务接收 HTTP 请求，调用下游、等待响应，再执行计算；线上曾出现突然加剧的锁竞争。为复现，作者在 96 逻辑 CPU 的机器上，固定每项工作约 350μs、临界区约占 1%，扫描并发度。Go 1.9 的结果出现明显断崖：

trace 显示，崩塌时从一次 Unlock 开始到下一位等待者的 Lock 即将返回，交接约需 60–70μs。作者还测试了解锁后显式 Gosched，并在后续评论中报告运行时补丁 CL 200577 改善了该基准的崩塌。

为什么不是一次内存操作的耗时？这里量的是完整锁交接：同步机制处理、等待者变为就绪、排队获得执行机会及恢复执行，都可能计入其中。多核缓存一致性与 OS 调度也可能影响成本，但原帖没有拆分各项贡献，不能直接把 60–70μs 归因于缓存行争用或内核唤醒。尤其要分清：唤醒 G，不一定需要唤醒休眠的 OS 线程。

“并发度”不是总 goroutine 数。贴出的基准代码创建 4 × GOMAXPROCS 个 worker，再通过信号量限制进入计算和争锁循环的数量。该硬件配置下总 worker 可为 384，而信号量上限分别为 45、46 等。对照实验改变的是参与工作的并发上限。见 作者对代码的澄清。

2.2 调度与锁，怎样一起放大问题？

一把共享锁一次只允许一个持有者推进。持锁计算结束后，下一个等待者还需要被交接、恢复并真正开始执行；这段成本可能大于原本很短的临界区。更多参与者会增加竞争，却不会让那段串行工作变成并行。

Go Mutex 的公平性策略与 G 的 park、ready、再次调度会影响交接。原帖评论对“饥饿模式为何持续”的解释包含明确标注的未验证假设，不能写成对每次线上故障都成立的根因。实际排障首先要定位竞争的是哪把锁、由谁持有、交接中慢在哪里。

2.3 迁移到自己的服务：先定位锁，再决定怎么限并发

  1. 画出吞吐随并发度的曲线。固定 P、CPU 配额和请求分布，逐档增加在途上限，记录吞吐、P99、在途数和错误率。区分正常收益递减与突然下跌。
  2. 用 mutex profile 找竞争来源。它把等待成本归到引起竞争的持锁者、通常是解锁路径的调用栈；不能把热点栈直接理解成“这个函数本身计算了这么久”。配合 goroutine 栈确认等待者。
  3. 用短 trace 拆时间。区分同步阻塞、被唤醒后的 runnable 等待、真正执行；需要时在自己的关键流程加 trace region。CPU profile 只看消耗 CPU 的部分，不能单独量出所有锁等待。

确认瓶颈后，可以缩短临界区、按 key 分片、批量合并更新或改为局部聚合，并在共享资源入口设置有界并发。若限制并发有效，还要计入入口排队、拒绝和超时：不能只让已被接纳的请求看起来更快，把等待藏到队列外。

验证时保持相同到达压力，比较整体成功吞吐和端到端延迟；同时再跑一次饱和压测，确认容量变化。若是在有限任务批处理中，固定总任务量和结果，再比较总完成时间。

历史修复不能漏掉。报告者在 补丁验证评论 中确认 CL 200577 改善了当时的测试。这个案例说明怎样取证和理解竞争，不证明 Go 1.23.4 或当前版本仍有同一缺陷；也不支持给所有 Unlock 后面添加 Gosched。

工具语义：Mutex profile；一般性处理建议为本文补充，不是原作者已经部署并验证的修复清单。

回到原理：waiting 与 runnable · Gosched 的作用与边界 · 实际命令：抓取 profile 与 trace

03Grab：2.05 核变成 1.94 核，消费能力为何跳变？

来源：Grab 工程博客，2023-05-23。Kafka → S3 的真实流水线；原文没有给出完整工具链版本和全部资源配置。

3.1 原始记录：代码没改，Kafka lag 却涨了

Grab 的 SinktoS3 流水线用多个 worker 并行执行计算密集工作，原本改善了消费能力。随后 VPA 将 CPU 配置从 2.5 核逐步调到 2.05、1.94 核；跨到 2 核以下后，消费速率明显下降并积压。团队对齐资源、CPU 与消费曲线，把 VPA 最小 CPU 配置设回 2 核后，处理能力恢复。

原文将原因关联到其使用的自动 GOMAXPROCS 配置：非整数配额向下取整，P 因而可能从 2 变为 1。资源数值只小幅变化，程序的并行名额却发生整数跳变。

3.2 为什么 CPU 使用率降低，不代表系统更轻松？

一个纯计算阶段若只能同时执行一份普通 Go 工作，即使 CPU 带宽预算接近两核，它也未必能把预算吃满。这时可能同时出现“CPU 使用下降”和“队列积压增加”。如果只盯着 CPU 百分比，自动化系统或人都可能误判为资源仍有富余。

这是根据 P 数限制所作的解释；真实流水线还有 I/O、GC 和各阶段并发配置。原文部分段落把 CPU requests、limits、GOMAXPROCS 与 throttling 的关系说得过于笼统：P=1 导致计算并行度不足，与 cgroup 真正耗尽带宽而被节流，是两个需要分别测量的问题。不能仅凭 Kafka lag 或低 CPU 就宣布发生了节流。

3.3 迁移到自己的服务：把资源变化和处理能力放到同一条时间线上

  1. 对齐三组记录。Kafka 输入/消费速率和 lag；VPA recommendation 与实际生效的 requests/limits；进程启动、重启及运行中的有效 GOMAXPROCS。确认跨过边界时 P 是否真的变化，还是仅仅配额改变。
  2. 检查资源实际在哪里生效。VPA 建议值、Pod 配置和进程所属 cgroup 的限制可能处于不同阶段；同时核对 cpuset 和父层限制。CPU request 是调度及争用分配的依据之一，不能直接当成执行上限。
  3. 区分限制。若 P 从 2 变成 1，先检查计算阶段能否并行；若 P 未变而 throttling 增加，走配额路径；若大量任务在等 S3 或内部队列，再查等待和下游。

针对确认的原因，为重负载流水线设置合适的最小资源与并行度，并明确自动配置的更新方式。验证不能只看“积压终于清掉”：还要看消费速率能否持续覆盖输入、单位消息 CPU 成本及稳定期延迟，避免补偿性追赶掩盖长期容量不足。

边界：本例中 worker 原本已经带来收益，资源调整又削弱了可用执行能力。Go 1.25 引入的 CPU limit 取整采用向上取整；默认 P 通常不低于 2，除非逻辑 CPU 数或 CPU 亲和性允许的数量小于 2。显式设置也会影响默认更新。见 容器默认行为说明 与 GOMAXPROCS 的具体规则；不能把“至少 2 核”推广成所有 Go 服务的要求。

回到原理：单 P 下的并发与并行 · 对照案例：P 过多时的配额问题

04CockroachDB：后台工作，消耗了在线请求的响应预算

来源：Cockroach Labs · Rubbing control theory on the Go scheduler，2022-12-15。生产数据库中的混合负载问题，配合受控压测和运行时插桩分析；不是一份逐分钟的线上事故报告。

4.1 原始记录：备份期间，前台长尾变差

CockroachDB 的在线查询与备份、扫描等工作共享执行资源。团队在前后台混合负载中观察到长尾恶化，平均 runnable 数未直接揭示原因。抽样请求追踪和调度指标进一步暴露等待；修改 RPC 插桩及运行时后，确认部分未解释的时间实际花在 runnable 状态。最终采用以调度延迟反馈的后台 CPU 准入控制，精细计量依赖定制运行时。

4.2 请求不是只排一次队

一个请求可能经历：处理入站消息、发起 RPC、等待响应、恢复后处理结果。每次由另一个 G 接棒，都可能重新经历“已就绪，等执行”。即使网络传输很快、每个处理函数的计算没有变，这些等待仍可能累积为明显的端到端延迟。

Go 调度器并不知道哪段业务是“客户正在等的查询”，哪段是“可以晚一点的后台扫描”。抢占让其他任务有机会推进，但它不提供业务优先级与延迟 SLO，也不保证一个请求在每次接棒时都能立刻运行。

4.3 迁移到自己的服务：把“CPU 忙”变成可验证的解释

  1. 先做可控干预。固定前台压力，分别暂停、限速和恢复后台任务，比较在线延迟。关联只负责提出怀疑，干预负责进一步检验。
  2. 沿请求追踪定位空白。确认时间是消耗在 SQL、网络、锁，还是就绪后等 CPU。分布式 tracing 帮助定位阶段，Go execution trace 帮助解释进程内部 G 的状态；它们不是同一种 trace。
  3. 看调度延迟分布。/sched/latencies:seconds 记录就绪后等待运行的时间。比较故障窗口与正常窗口的分布，同时检查 CPU 配额与节流；调度延迟高本身还不能区分是后台竞争还是外部 CPU 限制。
  4. 防止平均值掩盖局部等待。总 CPU、平均 runnable 数和单个函数耗时都正常，不足以排除某段请求链路经历了较长调度等待。

一般服务可先为后台工作设置独立的有界队列、并发上限和处理速率，按小批次推进，必要时分进程或实例隔离；准入等待放在尚未持有前台依赖的锁或其他稀缺资源的位置。再用在线 SLO、后台完成进度和 CPU 利用率共同验证，避免把后台工作一直饿住。

不要只补 Gosched。让出后仍是 runnable，下一轮仍会争取执行；它不限制后台工作累计吃掉的 CPU 时间。CockroachDB 的精细方案还包含控制器、预算分配与定制运行时能力。本文的普通服务建议不声称能复现其全部效果。也不能将某个调度延迟阈值当成所有服务的通用标准。

度量语义：runtime/metrics。直方图通常是进程生命周期累计值，窗口分布需要对同一桶边界做计数差分；分位值不能通过“前后 P99 相减”得到。

实际读取：调度延迟的窗口直方图与 P99 桶。

回到原理：异步抢占 · CPU 热点与调度等待的区别

05流媒体：忙于找工作，也是一种 CPU 开销

来源：golang/go #28808，2018-11。真实 UDP 流媒体应用的升级压测，以及简化复现程序；主要对照 Go 1.9 与 Go 1.11，Linux/amd64。

5.1 原始记录：业务代码没变，CPU 却增加

服务通过 HTTP 从本地缓存取数据，再以目标码率用 UDP 发送。每个会话由 ticker 周期唤醒发送 G，典型运行约 15μs、周期约 2.4ms。56 逻辑 CPU 的节点上运行 5 个实例；升级 Go 后，相同负载更耗 CPU。用旧业务代码重新编译也出现变化，缩小了问题范围。

CPU profile 指向 findrunnable 和工作窃取，schedtrace 又显示大量空闲队列。报告者将各进程 GOMAXPROCS 从 56 调至 12 后，对照压测的 CPU 消耗回到接近原水平。

5.2 大量空队列，为什么不等于没有成本？

短任务反复经历唤醒、执行、查找下一项工作和休眠，调度成本可能在每次很少的有效计算之外反复支付。较多 P 意味着潜在的查找范围更大；同机多个进程还各自运行一套调度器。原报告的解释是：定时器瓶颈缓解后，工作窃取开销变得突出。这属于其数据支持的历史问题分析，不是当前运行时所有负载的复杂度结论。

5.3 原帖怎样排除“就是业务改慢了”？

它使用了两条互补证据：同一业务代码换工具链，检查是否随工具链变化；再用简化模型复现相似的 runtime 热点。最后改变 P 做干预，观察 CPU 成本变化。这样的证据链，比看到火焰图里有 runtime 函数便开始改调度参数更有说服力。

5.4 迁移到自己的服务：用绝对成本验证

  1. 先固定工作。使用相同会话数、码率、包大小和机器环境；对照工具链与 P 时，分别保持其他变量一致。当前排障应先使用当前受支持的工具链，不必为了模仿历史而回退生产。
  2. 看 CPU 秒/有效工作量。对照相同窗口的总 CPU 与处理包数，而非只比较某个 runtime 函数占比。业务 CPU 降低后，即使调度 CPU 不变，其占比也会升高。
  3. 结合 trace 和 schedtrace。确认唤醒/休眠是否频繁、可运行任务是否很少；schedtrace 是采样快照，一次 runqueue=0 不能证明整个窗口没有排队，且该字段只表示全局队列。
  4. 对照更合适的 P 与任务粒度。如考虑合并唤醒、按批发送或改变定时策略，还要验证发送抖动与码率目标；减少唤醒可能损害业务时序。

原帖的 P=12 是该机器、多个进程与特定负载下的 workaround，既不是“56÷5 的标准答案”，也不是每个流媒体服务的推荐值。验证必须同时保住吞吐、时序质量和错误率，不能只把 CPU 曲线压低。

历史边界：本例中的运行时函数拼写、定时器实现与具体开销属于当年的工具链。它展示的是定位路径，不证明当前 Go 必然存在同样的扩展性问题。原帖附有完整简化程序，可用于研究；本文未将其输出冒充为本机重测结果。

06实际排查：每份证据回答一个问题

下面是本文补充的通用取证步骤，供迁移到自己的服务时使用。命令中的地址、进程和文件名都是示例；它们不是上述公司公开的实际环境，也不是本页已经执行的现场记录。

6.1 先把“变慢”定义清楚

有限任务：固定输入、总任务量与结果，比较总完成时间。在线服务：固定到达率和请求分布，比较成功吞吐、端到端延迟、拒绝和超时，并单独测试饱和容量。若压测客户端始终“收到响应才发下一次”，服务越慢它发得越少，可能掩盖排队和过载。

至少记录：目标实例的二进制/工具链版本、CPU 配置、生效的 GOMAXPROCS、worker/在途上限、输入速率、成功速率、P50/P99、错误率、队列长度以及 CPU 成本。多副本环境应选同类实例对照，避免某次流量倾斜被误认为参数收益。

// 放在目标进程的启动日志或诊断路径中，需要导入 log 和 runtime。
// 实际 P 数应从运行中的目标进程读取；另开一个 Go 程序测不到它。
log.Printf("go=%s platform=%s/%s NumCPU=%d P=%d",
    runtime.Version(), runtime.GOOS, runtime.GOARCH,
    runtime.NumCPU(), runtime.GOMAXPROCS(0))

启动日志只表示启动时状态。资源或并行度会动态变化时，还需要运行期观察；不同版本的默认更新行为、库的一次性初始化与显式设置要分别核对。

6.2 CPU、锁、G 状态：分别抓取，分别解释

以下以目标服务已在受控的 127.0.0.1:6060 提供标准 net/http/pprof 接口为前提。Linux/macOS 用 curl；Windows PowerShell 用 curl.exe 执行相同参数，避免旧版 PowerShell 的 curl 别名差异。分析时使用与采样二进制对应的 service；Windows 为 service.exe。

# CPU：当前 CPU 时间花在了哪里？
curl -fS -o cpu.pprof "http://127.0.0.1:6060/debug/pprof/profile?seconds=30"
go tool pprof -top ./service cpu.pprof
go tool pprof -top -cum ./service cpu.pprof

# goroutine 快照：当前都卡在哪些调用栈？
curl -fS -o goroutines.txt "http://127.0.0.1:6060/debug/pprof/goroutine?debug=2"

# 单独选择一个短窗口录制执行追踪：G 如何切换状态？
curl -fS -o execution.trace "http://127.0.0.1:6060/debug/pprof/trace?seconds=5"
go tool trace execution.trace

在 pprof 中，flat 是函数自身的采样成本，cum 包含被调用路径；它们不能沿调用链重复相加。在 trace 中，找到目标 G，区分 Waiting → Runnable 与 Runnable → Running，再与请求关键阶段对齐。

需要查锁竞争或同步等待时

mutex、block profile 需要目标进程启用采样。例如，在已有的受控诊断开关内使用以下 API；采样强度应按开销验证，并在取证结束后恢复原配置。

// runtime 包；示例采样强度，不是统一生产默认值。
// mutex：按竞争事件采样；返回旧配置，便于恢复。
previousMutexFraction := runtime.SetMutexProfileFraction(10)
defer runtime.SetMutexProfileFraction(previousMutexFraction)

// block：按阻塞时长采样，单位为纳秒；此示例约每毫秒阻塞量一次。
// API 不返回旧值，原有配置须由应用自己保存，再在取证后恢复。
runtime.SetBlockProfileRate(1_000_000)
# 在 Go 1.23.4 标准 pprof handler 上，seconds 请求窗口增量 profile。
# 按需选择一种抓取；不要将示例理解成必须同时启用全部采样。
curl -fS -o mutex.pprof "http://127.0.0.1:6060/debug/pprof/mutex?seconds=30"
go tool pprof -top -sample_index=delay ./service mutex.pprof

curl -fS -o block.pprof "http://127.0.0.1:6060/debug/pprof/block?seconds=30"
go tool pprof -top ./service block.pprof

mutex profile 主要观察已经完成的竞争事件，并归因到造成等待的持锁者栈；它不保证解释一把永远不释放的锁。遇到程序挂住，结合当前 goroutine 栈沿持锁/等待关系查。窗口结束时仍未结束的等待，也不能仅靠增量 profile 的数值完整衡量。

证据能回答单独不能证明
CPU profile采样 CPU 时间的热点、调用链。所有阻塞耗时；runtime 占比高就一定调度异常。
goroutine 栈采样时的调用位置与等待线索。历史等待分布；一次快照就证明泄漏或吞吐瓶颈。
mutex / block profile锁竞争或同步等待的累计/窗口成本。一条请求的完整墙钟耗时；永不结束的等待全貌。
execution traceG 的状态、唤醒、调度与执行过程。仅凭长 runnable 等待就判定是业务并发过多。
cgroup CPU 统计带宽限制、节流发生情况及窗口变化。业务里究竟是哪段计算或哪个请求触发压力。

命令与采样语义：net/http/pprof、runtime/pprof、SetMutexProfileFraction、SetBlockProfileRate、Go Diagnostics。采样和 trace 自身有开销，应按需分开采集，并保留同等开销的对照条件。

补上调度延迟：读取窗口内新增的样本

runtime/metrics 直接读取当前进程的运行时指标，不走 pprof HTTP 接口。/sched/latencies:seconds 返回累计直方图：桶边界是秒，每个计数对应 [下界, 上界)。先保存第一次采样，再读取第二次，以桶计数之差估算窗口内新增样本的分布。

完整 Go 示例：保留快照、做差分，找到 P99 所在桶

保存为 sched-latency.go，运行 go run sched-latency.go 可验证读取流程；单独运行只测它自己。用于业务排查时，将函数接入目标服务的受控诊断流程，在后台调用 reportSchedLatency(5 * time.Second)，让窗口覆盖实际负载；不要在请求处理路径中等待这 5 秒。

package main

import (
    "fmt"
    "runtime/metrics"
    "time"
)

func reportSchedLatency(window time.Duration) {
    samples := []metrics.Sample{{Name: "/sched/latencies:seconds"}}
    metrics.Read(samples)
    if samples[0].Value.Kind() != metrics.KindFloat64Histogram {
        fmt.Println("当前运行时不支持该直方图指标")
        return
    }
    h := samples[0].Value.Float64Histogram()
    // 必须复制底层切片；再次 Read 可能复用并覆盖原有存储。
    before := append([]uint64(nil), h.Counts...)
    buckets := append([]float64(nil), h.Buckets...)

    time.Sleep(window)
    metrics.Read(samples)
    after := samples[0].Value.Float64Histogram()
    // 同一进程、同一指标的桶边界不变；这里只读，不修改运行时存储。
    delta := make([]uint64, len(before))
    var total uint64
    for i, n := range after.Counts {
        if n < before[i] {
            fmt.Println("计数回退，跳过此窗口")
            return
        }
        delta[i] = n - before[i]
        total += delta[i]
    }
    if total == 0 {
        fmt.Println("窗口内没有新增样本，不能估算 P99")
        return
    }

    // ceil(0.99 * total)，用整数避免浮点取整与乘法溢出。
    rank := total - total/100
    var cumulative uint64
    for i, n := range delta {
        cumulative += n
        if cumulative >= rank {
            fmt.Printf("window=%s samples=%d p99_bucket_ms=[%.6g, %.6g)\n",
                window, total, buckets[i]*1e3, buckets[i+1]*1e3)
            return
        }
    }
}

func main() {
    reportSchedLatency(5 * time.Second)
}

输出中的 samples 是指标新增记录的样本数，不是业务请求数；运行时也可能对调度事件采样。没有新增样本不等于延迟为零。p99_bucket_ms=[a, b) 表示采用最近秩法得到的样本 P99 落在该毫秒区间，不是精确到某个小数的 P99；若上界为 +Inf，就没有有限的桶上界。

读取流程是：复制累计快照 → 等待观察窗口 → 再次读取 → 桶计数差分 → 从窗口分布找分位桶。不要只拷贝直方图指针或切片头；也不要直接拿进程启动以来的分布，解释刚刚发生的短时尖峰。新增记录的等待可能跨越窗口起点，因此这也不是把等待时长精确裁剪到这 5 秒内。

指标覆盖整个进程，不能单独归因到某个接口或后台任务。P99 桶上移时，再结合请求追踪、execution trace 和 CPU 节流证据定位原因。样本很少的窗口不适合据此判断长尾趋势。

API 依据：metrics.Read 的存储复用规则、Float64Histogram 的桶边界与计数；指标定义另与 GMP 主文使用的 Go 1.23.4 源码 核对。

6.3 检查 CPU 配额：先找对 cgroup，再看增量

以下仅适用于 Linux。先根据目标进程的 /proc/PID/cgroup 与挂载信息定位它所属的 cgroup；容器命名空间、宿主机路径和进程看到的路径可能不同。不能在宿主机随手读取根目录的 cpu.stat，就把它当成某个容器的统计。

# POSIX shell；将 12345 换成当前命名空间可见的目标进程 PID。
appPid=12345
cat "/proc/$appPid/cgroup"
cat "/proc/$appPid/mountinfo"

# cgroup v2：仅当此目录确实对应目标进程时使用这个示例路径。
cg=/sys/fs/cgroup
cat "$cg/cpu.max"
date -Is
cat "$cg/cpu.stat"
sleep 10
date -Is
cat "$cg/cpu.stat"

cpu.max 形如 200000 100000，表示每 100000μs 周期有 200000μs CPU 时间预算，即 2 核等效带宽；这是说明格式的假设值。max 表示该层不设此上限，还应检查父层约束。cpuset 则是另一类限制。

用途cgroup v2cgroup v1 的 CPU controller
配额 / 周期cpu.maxcpu.cfs_quota_us / cpu.cfs_period_us；quota 为 -1 表示该层不限。
节流次数cpu.stat 中的 nr_throttled同名字段。
节流时间throttled_usec，微秒。throttled_time，纳秒。

分析两个采样间的增量，确认窗口覆盖异常。Δnr_throttled / Δnr_periods 在分母大于零时可以反映发生节流的周期比例，但不是“CPU 损失百分比”；节流时间也不能不加解释地除以墙钟时间，就称作单请求延迟或精确损失。目标层未记录节流，也应检查祖先层的带宽约束，不能直接排除父层节流。

接口依据：Linux cgroup v2 · CPU interface files、CFS Bandwidth Control。Kubernetes requests / limits 的区别见 官方资源管理文档。

6.4 用 schedtrace 看线索，不把快照当成全过程

这通常需要在启动受控实例时配置，以下各例只影响该次子进程或在结束后恢复环境变量；请保留原有 GODEBUG 项。示例只启用每秒调度摘要，目标程序名为 service。

Linux / macOS POSIX shell 
GODEBUG="${GODEBUG:+$GODEBUG,}schedtrace=1000" ./service
Windows PowerShell 
$savedDebug = $env:GODEBUG
try {
    $env:GODEBUG = if ([string]::IsNullOrEmpty($savedDebug)) {
        "schedtrace=1000"
    } else {
        "$savedDebug,schedtrace=1000"
    }
    .\service.exe
} finally {
    $env:GODEBUG = $savedDebug
}
Windows cmd 
rem 新开一个子 cmd；脚本内部使用 setlocal，退出后不会改父会话。
rem 将以下内容保存为诊断用 .cmd，与 service.exe 放在同一工作目录。
@echo off
setlocal
if defined GODEBUG (
    set "GODEBUG=%GODEBUG%,schedtrace=1000"
) else (
    set "GODEBUG=schedtrace=1000"
)
service.exe
endlocal

重点看 gomaxprocs、idleprocs、spinningthreads、全局 runqueue 与方括号里的各 P 本地队列长度。结合多个样本与 profile 判断；某一秒队列空，不代表这一秒内没有瞬时拥堵。摘要也不是 G 状态转换日志。

6.5 用什么结果，才算改对了？

怀疑方向干预需要同时改善或守住的结果
配额与 P 不匹配单独调整 P 或 CPU 配额。节流窗口变化、成功吞吐、P99、成本；收益与取舍明确。
锁竞争减少竞争、调整资源入口的并发上限。竞争成本下降；同到达压力下端到端延迟、拒绝率与成功量合理。
整数边界 / 自动缩容调整资源下限或自动配置策略。实际 P 与配额符合预期；长期消费能力覆盖输入，lag 不再持续增长。
后台争用前台限制后台预算、分批推进或隔离。在线 SLO 达标；后台也能在要求的时限内完成。
短任务调度开销对照 P、唤醒方式或任务粒度。CPU 秒/有效工作量下降；吞吐、时序、抖动与错误率不退化。

每次只改一个关键变量，保留原配置与回退路径，重复对照。解释要落在证据上：究竟减少了哪种等待或成本，为什么业务指标因此改善；“goroutine 数少了”本身不是结论。
