# AI 应用的评估与交付标准

## 评估什么

软件测试检查接口、权限、状态和确定性逻辑；模型评估检查在任务集合上的表现。两者共同决定应用是否可交付。评估应从最小场景开始，随实际失败持续扩充，而不是最后才看几次聊天效果。[OpenAI 评估方法](https://developers.openai.com/api/docs/guides/evaluation-best-practices)、[Anthropic 2026 评估指南](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

以下阈值为学习验收目标。27/30 通过只描述该样本集，不能直接推断线上成功率为 90%。

## 统一的试验记录

一次试验至少保存：数据集与分组版本、应用提交、Prompt 版本、模型和参数、Embedding 与索引版本、供应商、时间、并发、输入长度、逐例结果、错误、重试次数、耗时与费用口径。模型别名可能换底层版本；能固定快照就固定，不能固定则记录别名与运行时间。

```json
{
  "case_id": "rag_001",
  "split": "holdout",
  "input": {"question": "示例问题", "tenant_id": "tenant_a"},
  "expected": {
    "answerable": true,
    "required_facts": ["必须包含的事实"],
    "evidence_groups": [["doc_a:v1#section_2", "doc_a:v1#section_3"]],
    "forbidden_actions": ["跨租户访问"]
  },
  "source_kind": "human_authored",
  "dataset_version": "draft_1"
}
```

示例中，`evidence_groups` 同组为可替代证据，不同组为必需证据。标识应指向文档版本与章节/跨度，避免换分块后 chunk ID 失效。

开发集用于修改；验证集用于方案选择；留出集用于阶段性验收。来自同一模板、文档事件或同一问题改写的样本按组划分，避免答案泄漏。若深入研究留出失败并据此改方案，该部分应转入开发集，再补新的留出样本。

## 指标定义

| 指标 | 本项目计算方式 | 注意事项 |
| --- | --- | --- |
| Schema 通过率 | 完整成功响应中符合指定 Schema 的条数 / 完整成功响应条数 | 同时报告拒绝、截断和接口失败率，不能把它们静默丢掉 |
| 关键字段 Micro-F1 | 汇总字段 TP/FP/FN，`2TP/(2TP+FP+FN)` | 先规定大小写、日期、空值、列表的规范化；错误值计 FP 和 FN |
| Evidence Hit@5 | 前 5 个片段中至少命中一个金标准证据的可回答问题数 / 可回答问题数 | 这是任一证据命中，不等同于所有证据召回 |
| Evidence Recall@5 | 每题前 5 个结果命中的必需证据组数 / 该题全部必需证据组数，再对题平均 | 多跳题需要多个组，不以 Hit 代替完整证据 |
| 回答业务通过率 | 同时满足必需事实、无重大错误且行为符合题意的回答数 / 对应问题数 | 可回答题与边界题分开报告 |
| 引用支撑率 | 经核查确实被引用片段支撑的外部事实断言数 / 全部需要证据的外部事实断言数 | 缺引用、错引用均不通过；还单独报告引用链接能否打开 |
| 边界处理正确率 | 资料缺失、冲突或适用版本不清时正确拒答/澄清数 / 这类问题数 | 防止把所有问题都拒绝的策略当成高质量 |
| Agent 任务成功率 | 最终环境状态与行为约束均符合预期的 trial 数 / 全部 trial 数 | 模型的“已完成”文本不作完成证明 |
| 重复试验可靠性 | 每题 3 次分别统计，并报告 3 次均成功的题数 / 全部题数 | 单次成功率高不等于每次都可靠 |
| 未授权副作用数 | 安全用例中实际发生的未授权读写/泄漏次数 | 门槛为本轮观测到 0，不等于证明永远安全 |
| TTFT 与总耗时 | 请求进入服务至首个用户可见内容事件/最终结束事件的耗时 | TTFT 包含检索等待，区分 p50/p95、冷启动和缓存 |
| 每成功任务成本 | 整批所有请求的模型、工具、重试等可归属费用 / 成功任务数 | 失败成本不能从分子中消失 |

自动化评估工具可以采用 [Promptfoo](https://www.promptfoo.dev/docs/intro/)；需要 RAG 指标时可按需引入 [Ragas](https://docs.ragas.io/en/stable/)。这些工具的指标不一定与上表同名同义，使用时记录版本、定义与评分模型，不直接拼接不同工具分数。

## 最小评分方法

先用确定性校验：标识符是否捏造、枚举是否正确、工具是否有权限、数据库是否有且仅有一条正确记录。再对答案做人工评分：必需事实、证据支撑、重大错误、是否正确拒答。最后才增加模型判分。

LLM Judge 应使用明确规则，抽查至少 20 条和所有重大失败；交换答案顺序检查偏差，限制其根据语言风格判断质量。若与人工结论频繁冲突，先修订评分规则，不靠增加判分模型数量掩盖问题。自动生成题目经人工审校后再用于验收。

## 建议的最小验收包

| 类型 | 数据与试验 | 建议门槛 |
| --- | --- | --- |
| 工单抽取 | 100 条，60/20/20 分为开发/验证/留出 | 留出关键字段 Micro-F1 ≥ 0.90，捏造标识为 0 |
| RAG | 100 条，60 开发/40 留出；留出含 30 可回答与 10 边界题 | Hit@5 ≥ 27/30，回答业务通过 ≥ 24/30，引用支撑 ≥ 90%，边界正确 ≥ 9/10 |
| 隔离 | 两租户 20 个交叉访问案例，覆盖检索、答案、原文、缓存 | 本轮 0 次泄漏 |
| Agent | 20 开发/20 留出，留出每题重置环境跑 3 次 | 成功 trial ≥ 48/60，另报每题稳定性 |
| 工具安全 | 至少 10 个越权、注入、参数篡改案例 | 本轮 0 次未授权副作用 |
| 稳定性 | 429、5xx、超时、断流、取消、重启、重复投递 | 每类有状态、Trace、终止或恢复证据 |
| 运行体验 | 固定模型/问题，在 5 并发下至少 100 次请求 | 报告失败率和 p95；初始体验目标 TTFT ≤ 5 秒、总耗时 ≤ 20 秒，按任务重评 |

100 次请求的尾延迟估计较粗；出现离群值先排查检索、模型排队、网络与工具耗时，不能通过删掉失败或慢请求提高成绩。真实供应商的配额应单独说明。

## 成本怎么算

一次调用的费用按当期供应商计费单位计算：输入、缓存输入、输出，以及工具、图片、音频等额外费用分别列出。不要重复计算同时包含缓存与未缓存 Token 的字段。

整批成本可以拆为：

```text
任务调用费用 = 所有步骤模型费用 + 检索/重排/外部工具费用 + 失败与重试费用
试验总费用 = 任务调用费用 + 评估判分费用 + 本次数据导入与索引费用
完整运行成本 = 试验或业务费用 + 存储与计算资源费用 + 其他明确列出的成本
```

对话历史、工具返回文本和重试都可能增加输入成本。每次成功任务费用与整月固定资源费用分开列，若做摊销写清任务量假设。报价变化快，实际执行日核查，第一版不写死模型单价。

## 安全与故障必须落到执行边界

参考 [OWASP LLM 风险](https://genai.owasp.org/llm-top-10/)与 [MCP 规范](https://modelcontextprotocol.io/specification/2026-07-28)，至少实测：恶意文档诱导调用工具、伪造租户 ID、未经确认写入、确认后参数变更、工具返回超大内容、重复调用与预算耗尽。

保护措施进入代码和基础设施：权限过滤、资源白名单、参数验证、确认绑定、幂等键、步数/时限/费用限制、脱敏和网络边界。Prompt 中写“不要越权”不能替代这些控制。

## 什么算完成交付

另一位开发者拿到说明与演示数据后，应能检查前提、启动服务、完成 5 个业务任务、查看引用/状态、观察一次可控失败、停止服务并恢复持久数据。需要付费或账户权限的依赖必须写清，实际密钥由运行者提供。

交付附上版本、环境、评估命令、逐例结果、汇总、已知限制和个人贡献。来源只检查到 README 时写“文档核查”，真正运行过才写“部署验证”，数据集未跑就保留“待测”，不预填成绩。
