# 大模型应用开发的岗位与能力

## 这个方向实际交付什么

“大模型应用开发工程师”没有覆盖所有公司的统一职位定义。这里按公开岗位与产品工程实践使用一个工作定义：**把模型能力、业务数据、工具和服务组合成可用产品，并对效果、成本、延迟和运行可靠性负责。**

例如客户说“我想退掉昨天买的商品”，后端需要识别意图、查询订单、核对规则、展示结果。模型可以帮助理解自然语言和整理解释；订单归属、退款资格、金额计算与实际写入仍由业务服务确定。

可以把模型看成接入系统的新型外部依赖：它很会处理语言，输出却带有不确定性。这个比喻有助于理解超时、隔离和观测的必要性；边界在于模型还会生成看似合理的错误内容，因此 HTTP 200、JSON 合法和无异常都不足以证明业务成功。[结构化输出说明](https://developers.openai.com/api/docs/guides/structured-outputs)、[评估方法](https://developers.openai.com/api/docs/guides/evaluation-best-practices)

## 岗位分工与推荐入口

| 岗位方向 | 常见交付 | 学习重点 |
| --- | --- | --- |
| AI 应用后端或 AI 产品工程师 | 模型接口、RAG、工作流、业务集成、服务运行 | 软件工程基础、模型效果与产品闭环 |
| Agent 工程师 | 工具契约、执行循环、状态、恢复、权限、任务评估 | 完成基本应用和 RAG 后进入 |
| AI 平台或 LLMOps 工程师 | 网关、配额、可观测、数据与评估平台、运行环境 | 适合偏基础设施兴趣，仍要理解效果 |
| 解决方案或交付工程师 | 场景发现、原型、系统集成、客户验收 | 要补业务表达、边界管理和效果证明 |
| 模型算法或后训练工程师 | 数据训练、微调、对齐、模型实验 | 可作为后续分支，先补深度学习和实验能力 |
| 推理系统工程师 | GPU、批处理、KV Cache、量化、分布式推理 | 与应用服务有交集，但学习投入不同 |

这些方向会混在同一 JD 中。筛选时看“交付物和日常任务”，不要只看职位名称。

这些样本共同提示，应通过项目说明模型评估、上下文管理、数据与工具接入、生成失败处理等能力。已有的软件工程经验可以提供基础，但使用 AI 辅助编程本身不能替代 AI 应用的设计、评估与运行实践。

## 先掌握的概念及其边界

| 概念 | 准确含义和生活化理解 | 容易混淆的边界 |
| --- | --- | --- |
| Token 与上下文 | Token 是模型处理文本等输入的基本单元；上下文是本次推理可用的信息，像当前工作桌面 | Token 不等于汉字；窗口大不等于能可靠利用所有内容 |
| Prompt | 输入中的任务说明、约束和示例，像工作说明书 | Prompt 不能代替服务端授权或数据校验 |
| Structured Outputs | 按支持的 JSON Schema 约束输出结构 | 格式合规仍可能有事实错误、拒绝或未完成响应 |
| Embedding | 将输入映射为可比较的数值向量，用于语义检索等 | 相似度不是事实真伪，也不是校准后的置信概率 |
| RAG | 把检索到的外部资料引入生成过程，像先查手册再作答 | 原论文有联合训练设计；日常应用常用独立检索流水线，不要求复现训练 |
| Tool Calling | 模型提出工具名和参数，由应用执行并把结果返回 | 模型发出调用不代表已经执行，更不代表有权限 |
| Workflow | 程序确定主要执行路径，部分节点可以调用模型 | 节点多不自动构成自主 Agent |
| Agent | 常见工程用法是模型依据工具反馈循环决定下一步 | 不同厂商定义有差异；自主程度越高越需要终止条件和效果验证 |
| MCP | 连接模型应用与外部数据、工具的开放协议 | 提供接口标准，业务授权仍由应用实施，也不等于 Agent 本身 |
| 微调 | 用任务数据进一步更新已有模型参数 | 不能作为持续更新知识库和权限系统的替代品 |

定义参考：[Hugging Face 课程](https://huggingface.co/learn/llm-course/chapter1/1)、[RAG 原论文](https://arxiv.org/abs/2005.11401)、[Anthropic Agent 工程模式](https://www.anthropic.com/research/building-effective-agents)、[工具调用](https://developers.openai.com/api/docs/guides/function-calling)、[MCP 规范](https://modelcontextprotocol.io/specification/2026-07-28)。

## 软件工程基础与 AI 应用能力

| 软件工程基础 | AI 场景新增问题 | 实践证据 |
| --- | --- | --- |
| HTTP/RPC 与接口设计 | 不同供应商事件、工具、usage 和错误语义有差别 | 一个薄适配层和能力矩阵，不隐瞒不支持的功能 |
| Context、超时与并发 | 多轮调用可能累计时间和费用，客户端断开后仍继续生成 | 取消贯穿链路、调用预算、最大步数、受控并发 |
| 数据库与缓存 | 文档版本、Embedding 版本、权限和缓存隔离 | 更新删除一致性实验、跨租户反例 |
| 队列与后台任务 | 解析、索引、长 Agent 任务需恢复 | 幂等任务、检查点、失败重放和死信记录 |
| 日志和指标 | 还要知道模型为什么答错、哪次检索没找到证据 | 检索与工具轨迹、Prompt/模型版本、脱敏记录 |
| 自动测试 | 一个正确答案可能有多种表述，输出还会波动 | 固定评估集、业务判分、多次试验与人工校准 |
| 全栈项目 | 用户需要引用、取消、补充信息和确认动作 | 能演示失败与恢复的完整 UI 闭环 |

## 技术栈的学习顺序

推荐先选择 Python 或 Go，用单服务、PostgreSQL 和一个模型供应商构建闭环；文件存储按需要加入。需要语义检索时加入 pgvector，需关键词检索时再增加或调整检索实现。Redis、独立向量库、消息系统都由实测需求触发，不一次性搭齐。

Python 路径先掌握虚拟环境、类型、异常、异步 I/O、JSONL、pytest 和基本服务开发，再学习模型 SDK、数据处理、评估与 LangGraph。Go 路径先掌握接口、Context、HTTP、并发与测试，再学习供应商 SDK 和 Eino 的组件、Graph、ADK。两条路径均需独立完成模型接入、检索、工具执行与部署验证。[Eino](https://www.cloudwego.io/docs/eino/overview/)、[LangGraph](https://docs.langchain.com/oss/python/langgraph/overview)、[pgvector](https://github.com/pgvector/pgvector)

解析/OCR、模型运行库或服务复用需要跨语言时，通过 HTTP 或任务消息连接独立服务，并明确超时、错误和数据契约。

## 必修与后置内容

**必修**：模型调用与限制、业务结构化、评估集、Prompt/上下文版本、检索质量、工具权限、取消与恢复、成本、可观测、文档和交付。

**够用的基础**：理解下一 Token 预测、训练与推理、Transformer/Attention 的作用、向量相似度、采样参数、精确率/召回率和基础概率统计。能读懂并解释失败即可，不先要求推导整个训练过程。

**后置分支**：LoRA/QLoRA、SFT/DPO/强化学习、vLLM 部署、图检索、复杂多 Agent、语音实时交互、计算机操作。若目标 JD 明确要求，把相应分支提前；否则先用基线证明它解决了什么问题。[Hugging Face 进阶课程](https://huggingface.co/learn/llm-course/chapter1/1)、[vLLM](https://docs.vllm.ai/en/latest/getting_started/quickstart/)

## 选岗位时怎么使用这条路线

从目标城市的雇主官网收集 15 至 20 个岗位，记录日期、职级、语言、核心任务与必需经验。按“应用后端”“Agent”“平台”“算法”分组，识别共同要求与专项要求，再调整学习重点。

完成阶段 3 后进行岗位匹配与面试校准；完成阶段 5 后补充运行、质量和成本报告。
